1. INTRODUCTION                             *forge* *forge.nvim* *forge-intro*

Read GitHub and GitLab issues, pull requests and merge requests in Neovim.

Two commands, |:Issue| and |:PR|. Everything else is a mapping in the buffer
they open. Nothing to configure.

==============================================================================
2. REQUIREMENTS                                           *forge-requirements*

- Nvim 0.12+
- "gh" (GitHub CLI), authenticated: https://cli.github.com
- "glab" (GitLab CLI), authenticated: https://gitlab.com/gitlab-org/cli

Optional, one mapping each:

- ci.nvim, for "dc": https://forge.barrettruth.com/barrettruth/ci.nvim
- diffs.nvim, for "dd": https://forge.barrettruth.com/barrettruth/diffs.nvim
- vim-fugitive, for "dl": https://github.com/tpope/vim-fugitive

==============================================================================
3. COMMANDS                                                   *forge-commands*

:Issue [{target}]                                                     *:Issue*
:PR [{target}]                                                           *:PR*
    Open {target}. Without an argument, open the list for the current
    repository. {target} is any of: >
        :PR @
        :Issue .
        :Issue 41138
        :Issue #41138
        :PR !123
        :Issue neovim/neovim#41138
        :PR group/subgroup/project!123
        :Issue neovim/neovim
        :Issue https://github.com/neovim/neovim/issues/41138
        :Issue forge://github.com/neovim/neovim/issues/41138
<
    A target naming no repository uses the one the CLI resolves.
    |forge-repository|

    ":Issue" opens only issues. ":PR" opens only pull and merge requests. A
    bare number belongs to the command's own collection.

    "@" is the pull request for the current change. ":Issue @" is an error. A
    change with no pull request opens the new-pull-request page.

    "." is the reference under the cursor, from any buffer. A reference is
    "#41138", "!123", "neovim/neovim#41138", "group/subgroup/project!123", a
    github.com URL or a forge:// URI. Not a bare "owner/repo". Not a mention.
    Inside a view, |gf| does the same. |forge-gf|

    Anything else is a search. |forge-search| >
        :Issue label:bug is:open
        :PR review-requested:@me
        :Issue label:"good first issue" no:assignee
<
    |:command-modifiers| are honoured. The window is made once the forge
    answers. >
        :vertical Issue 41310
        :tab PR 41138
        :botright Issue neovim/neovim
<
                                                                   *forge-api*
The same two entry points in Lua: >lua
    require('forge').issue(target)
    require('forge').pr(target)
<

4. REPOSITORY                                               *forge-repository*

The repository is whichever gh or glab resolves in the current directory. In a
fork that is the base repository.

The forge is chosen by host. gitlab.com is GitLab, as is any host glab holds a
login for. Everything else is GitHub. A target naming no repository takes the
host of the "upstream" remote, else "origin".

Requests are made from the directory of the current buffer. Buffers are filed
under the forge's spelling of the name, whatever was typed.

A bare |:PR| also needs the current branch. git answers first. In a colocated
jj repository the bookmark on the current change answers instead. A change
wearing no bookmark is an error.

5. URIS                                                           *forge-uris*

Buffers are named with a "forge://" URI. Every view has exactly one name, and
that name is enough to rebuild it: >

    forge://{host}/{project}/{collection}            the whole list
    forge://{host}/{project}/{collection}?q={query}  the ones a search matches
    forge://{host}/{project}/{collection}/{number}   a single one
<
{host} is the forge, by hostname. {collection} is "issues" or "prs". "prs"
holds merge requests on GitLab. {project} is "{owner}/{repo}", or a GitLab
path of any depth: >

    forge://github.com/neovim/neovim/prs/41370
    forge://gitlab.com/gitlab-org/cli/issues/8022
    forge://gitlab.com/group/subgroup/project/prs/123
<
|:edit| on one opens it from anywhere, and reloads it from inside. A reload
returns to the first page. "R" keeps the page.

A query is percent-encoded. |:edit| by hand wants the "%" escaped: >
    :edit forge://github.com/a/b/issues?q=is:open\%20label:bug
<

6. BUFFERS                                                     *forge-buffers*

A single item has a 'filetype' of "markdown". Its comments are headings. A
list has a 'filetype' of "forge".

Both are scratch buffers: 'buftype' is "nofile", 'readonly' is set,
'undolevels' is -1 and 'modeline' is off. A buffer being fetched again sets
'busy'. Window options are applied wherever a view appears, and released when
that window shows something else.

Highlighting uses builtin |group-name| groups only.

                                                                     *b:forge*
Every view buffer carries a `b:forge` dictionary. The 'winbar' is drawn from
it, and a user mapping may read it. Present in both shapes: >

    kind       "list" or "item"
    label      what the winbar calls it, e.g. "PR", "MR"
    repo       the project's full path
    url        the address the forge gave it
<
In a list, and only in one: >

    pages      the current page, e.g. "1/3", or "1/?" where the last
               page is not known
    total      how many the list holds in all, absent where that is
               not known
    query      the search narrowing it, empty when there is none
<
In an item, and only in one. The last three are a pull or merge request's: >

    tag        its number, e.g. "#41138", "!123"
    title      its title
    about      what the winbar says after the state, empty when the
               branches say it instead
    state      the state as shown, e.g. "OPEN", "MERGED", "NOT PLANNED"
    state_hl   the highlight group that state is drawn in
    badges     its extra winbar segments
    stat       what it measures, drawn against the right edge
    id         what a mutation names it by
    can_update whether the forge will let you change it
    oid        the head it was drawn from
    can_squash        whether the forge would take each of the three
    can_merge_commit  merges, weighed before the menu is drawn
    can_rebase
    can_bypass whether a merge would bypass something to happen
    merge      the commit message the forge would write, keyed by the
               method that would carry it, absent where it writes none
    can_auto   whether a merge may be set to wait, and whether one
    can_unauto already waiting may be called off
    auto       the method a waiting merge would use, absent when none
               is waiting
    queued     whether the base branch merges through a queue, and
    in_queue   whether this one is in it
    base       the branch it merges into
    head       the branch it merges from, prefixed with the owner when
               that is a fork
    remote     the repository "dd" and "dl" fetch it from
    stack      which layer of its stack it is, "3/4", counted from the
               bottom, and empty where it is in none
    stack_kept whether the forge keeps that stack itself, rather than
               forge having derived the chain
<
An item is its title, then who opened it and when, then what is known about
it, then its body and the conversation under it: >

    # Support file:// without netrw

    ▎ superatomic  MEMBER  4 days ago
      Assignees:  clason
      Type:       Enhancement
      Parent:     #32280
      Labels:     uri, lifecycle
      Milestone:  0.13

    Nvim supports opening files with file:// syntax.

    ## Comments (2)

    ▎ yochem  CONTRIBUTOR  3 days ago

    As file:// are just urls this should be added to net.lua.
<
A row is drawn only when it has something in it. A pull or merge request says
"Reviewers" instead of "Type" and "Parent".

                                                                 *forge-stack*
A pull or merge request that is one of a chain of them draws the chain, after
the description and before the comments: >

    ## Stack (3/4)

      #147  util: add a dedupe helper
      #148  util: add a chunk helper
      #149  api: read the rate limit headers
      #150  api: stop paginating once the budget is spent
<
The layer nearest the trunk first, each one below built on the line above it,
and counted the same way, so "3/4" is the third line. Each number is drawn in
the colour of its state. The line being read is drawn in "CursorLine".

<CR> opens the layer under the cursor. "[s" goes to the layer above and "]s"
to the one below, wrapping.

Two layers sharing a base branch are named rather than ordered: >

    ## Stack (1/1)

      #157  idgen: allow a custom entropy source
      forks into #158, #159
<
Every layer of a chain is in the same repository.

Stack merging is unsupported. See |forge-limitations|.

A bar starts anything somebody wrote. Logins, labels and milestones are
highlighted. Anything that can be followed is underlined.

"@someone", "#123", "!123", "owner/repo#4" and "group/project!123" are marked
wherever a body holds one, except inside a fenced block. |gf| follows a
reference. |gx| opens a mention's profile.

                                                               *forge-address*
An address of the forge itself is drawn as the reference the forge draws in
its place. Inside neovim/neovim, a body reading >
    Fixed by https://github.com/neovim/neovim/issues/41138 upstream.
< is drawn >
    Fixed by #41138 upstream.
<
|gf| follows the reference. |gx| opens the address behind it. An address the
forge itself leaves whole, one on another host, and one inside a code span or
a fence are all left as they were written.

WARNING: comments written against a line of the diff are not shown. A change
reviewed in the diff shows fewer comments here than on its own page.

Every view sets a 'winbar': >

    ISSUES barrettruth/forge-fixture 1/2 (124)
    ISSUE #27 OPEN | a title that fits
    ISSUE #41309 NOT PLANNED | one nobody is going to do
    PR #151 MERGED | master <- a-branch                         +10 -2
    PR #152 OPEN | master <- them:their-branch CONFLICT FAILING | +7 -0
    MRS group/subgroup/project 1/1 (8)
    MR !12 OPEN | main <- a-branch                                +3 -1
<
A closed issue is drawn as the reason it closed (if possible, see
|forge-limitations|). An issue says its title after the state. A pull or merge
request says the branches it joins, base first.

A diffstat is drawn against the right edge. A badge says "CONFLICT" for a
conflicting merge, and "FAILING", "PENDING" or "EXPECTED" for the checks. Use
"dc" to investigate the checks.

7. MAPPINGS                                                   *forge-mappings*

Buffer-local defaults, only set if you have not mapped the |<Plug>| target:

    <CR>     <Plug>(forge-open)        Open the item the line names.
    o        <Plug>(forge-open-split)  The same, beside the list.
    gf       (see |forge-gf|)          Follow the reference under the cursor.
    -        <Plug>(forge-up)          Leave an item for its list.
    R        <Plug>(forge-refresh)     Fetch this view again, in place.
    ]i  [i   <Plug>(forge-next-page)   Page through a list. ]p and [p
             <Plug>(forge-prev-page)   in a pull or merge request list.
    ]s  [s   <Plug>(forge-stack-down)  Step down and up a stack. A count
             <Plug>(forge-stack-up)    steps that many layers.
    ga       <Plug>(forge-create)      Start something new, on the forge.
    gX       <Plug>(forge-web)         Open this view in a browser.
    gy       <Plug>(forge-yank)        Yank this view's URL.
    cc       <Plug>(forge-act)         Do something to this item.
    cE       <Plug>(forge-edit)        Edit its title and body.
    cD       <Plug>(forge-draft)       Draft it, or mark it ready.
    dc       <Plug>(forge-checks)      Its checks, in ci.nvim.
    dd       <Plug>(forge-diff)        Its diff, in diffs.nvim.
    dl       <Plug>(forge-log)         Its commits, in fugitive.
    g?       <Plug>(forge-help)        This section.

To rebind, map the |<Plug>| target and the default is skipped: >lua
    vim.keymap.set('n', '<C-]>', '<Plug>(forge-open)')
<

"R" keeps the current page and cursor position. |:edit| and a new page both
start at the first line.

"ga" opens the forge's own page for a new "thing".

"gX" opens what the buffer is showing in your browser. "gy" yanks the same
URL, and can take a register.

Use "cc" to perform a miscellany of actions in a |vim.ui.select()| menu:

    Change issue #27:
    Change pull request #151:
    Change merge request !12:
< and what it offers is >

    any of them                 edit title and body
    an open issue               close as completed, close as not planned
    a closed issue              reopen
    an open pull/merge request  convert to draft, close, merge
    a draft                     mark ready for review, close
    a closed one                reopen
    a merged one                nothing
<
                                                                *forge-direct*
Some of what "cc" offers has a key of its own, which skips the menu: >

    cE  Edit title and body
    cD  Convert to draft, or Ready for review
<
A direct key does what the menu entry does, and only where the menu would have
offered it. Otherwise it names the entry and does nothing.

"cD" is one key for two entries. The state decides which.


A merge is offered once per method the repository allows: "Squash and merge",
"Create a merge commit", "Rebase and merge". On GitHub the base branch's
ruleset narrows that. One with conflicts offers none of them, and neither does
a layer of a stack GitHub keeps. Deleting the branch on merge is unsupported.

A rebase is sent as it is picked. A squash and a merge commit open the commit
message first. |forge-merge|

                                                                  *forge-edit*
"Edit title and body" replaces the view. |CTRL-O| goes back to it. The buffer
is laid out as a commit message: the title on the first line, the body after a
blank line.

Its 'winbar' is the item's own with the state swapped for the mode: >

    ISSUE #166 EDIT
    PR #151 EDIT
<
":w" sends it. An empty title sends nothing. The buffer stays 'modified' until
the forge accepts it.

The buffer is wiped once no window shows it. 'modified' refuses ":q", ":bd"
and ":enew".

WARNING: ":hide" is not refused, and throws the text away.

                                                                 *forge-merge*
"Squash and merge" and "Create a merge commit" open the commit message they
would carry, in a split beside the item. It is laid out as a commit message:
the subject on the first line, the body after a blank line.

Forge behavior is respected: on GitHub it starts as the message GitHub itself
would write (perhaps a combination of commit messages), while on GitLab it
opens empty.

Its 'winbar' says which method, and says when the merge bypasses: >

    PR #151 SQUASH
    PR #151 MERGE COMMIT
    PR #174 SQUASH BYPASS
<
":w" sends it. The buffer behaves as |forge-edit|'s does. An empty subject
sends nothing.

"cc" is bound in every item. "dc", "dd" and "dl" only in a pull or merge
request. "dc" and "dd" replace the view. "dl" splits. ci.nvim returns with
"-". The way back from a diff or a log is |CTRL-O|.

The log is >
    git log --stat --reverse base..head
<
"dd" and "dl" fetch both ends first. The fetch goes into the repository of the
current directory, not the one the view names. The refs land under
refs/forge/. No branch, tag or working tree is touched.

"dl" points `b:git_dir` at that same repository, so `:Git` in the log aims
there too.

When run from outside the repository, "dd", "dl", and "dc" do not work.

                                                                    *forge-gf*
|gf| follows the reference under the cursor. |CTRL-W_f| opens it in a split.
In Visual mode the selection is used. This is 'includeexpr'. Nothing is bound.

|gf| takes the references ":Issue ." and ":PR ." take. A reference naming no
repository means the one whose view holds it. Surrounding punctuation is left
behind: "(#123)", "`#123`" and "#123." all follow to the same place. Anything
that is not a reference is handed back to Vim. |gf| on an ordinary path in a
body still opens the file.

"!123" is always a merge request. "#123" is an issue, except on GitHub, where
it means whichever collection the view holds.

In a list, <CR> opens the item the line describes, and in a stack the layer.
|gf| opens the reference under the cursor, which inside a title may be another
issue.

8. SEARCH                                                       *forge-search*

Search native Forges with a {target}, or open everything if unspecified:

Support varies per forge. For example, on GitLab, the query is matched against
the title and the description - qualifiers are unsupported.

                                                     *forge-search-completion*
|c_CTRL-D| and <Tab> complete a qualifier. They complete its value too, where
github's set of them is closed: "is:", "no:", "in:", "state:", "reason:",
"review:", "status:", "linked:", "draft:", "archived:" and "sort:".

A qualifier naming a person completes to "@me" and nothing else. A negation
completes the same. Labels, milestones and people do not complete.

==============================================================================
9. GITLAB                                                       *forge-gitlab*

Same as GitHub, but with GitLab semantics: a GitLab view says "merge request"
where a GitHub one says "pull request". It writes "!" in front of a number
instead of "#", and calls itself "MR" and "MRS" in the 'winbar'.

|:PR| remains the entrypoint. "prs" is still the collection its name holds: >

    :PR !123
    :PR group/subgroup/project!123
    :edit forge://gitlab.com/group/subgroup/project/prs/123
<

==============================================================================
10. LIMITATIONS                                            *forge-limitations*

Forgejo, Codeberg and Gitea are unsupported. Each forge has their own unique
(and endless) set of limitations - forge is best-effort.

Reviewing (approve, request changes, comment) is unsupported.

Pull requests/issues can only be made on the web.

Merging a stack is unsupported. The APIs are rather unstable as of cretion.

For similar reasons, deleting the respective branch on merge is unsupported.

==============================================================================
11. HEALTH                                                      *forge-health*

`:checkhealth forge` checks everything in |forge-requirements|. A missing glab
or optional plugin is a warning, not an error.
