1. INTRODUCTION                                                  *forge-intro*

Forge reads issues, pull requests and merge requests into Neovim buffers, from
GitHub and from GitLab. There are two commands, |:Issue| and |:PR|; every
other action is a mapping in the buffer they open. There is no setup()
function and nothing to configure.

Every view is named for the host it came from, so its name says which forge
answered; see |forge-uris|. On GitLab a pull request is a merge request, and
forge says it that way; see |forge-gitlab|.

==============================================================================
2. REQUIREMENTS                                           *forge-requirements*

  - Neovim 0.12 or newer
  - the "gh" CLI, authenticated (https://cli.github.com), for GitHub
  - the "glab" CLI, authenticated (https://gitlab.com/gitlab-org/cli), for
    GitLab

Optional, one mapping each:

  - ci.nvim, for "dc"
    https://forge.barrettruth.com/barrettruth/ci.nvim
  - diffs.nvim, for "dd"
    https://forge.barrettruth.com/barrettruth/diffs.nvim
  - vim-fugitive, for "dl"
    https://github.com/tpope/vim-fugitive

3. COMMANDS                                                   *forge-commands*

:Issue [{target}]                                                     *:Issue*
:PR [{target}]                                                           *:PR*
    Opens {target}. Without an argument, opens the list for the current
    repository.

    ":PR @" opens the pull or merge request for the current change. Nothing
    identifies the current issue, and ":Issue @" says so. A change with none
    yet opens the page a new one arrives on, and on GitHub gh pushes the
    branch.

    ":Issue ." and ":PR ." open the reference under the cursor, from any
    buffer. A reference is "#41138", "!123", "neovim/neovim#41138",
    "group/subgroup/project!123", a github.com URL or a forge:// URI; a bare
    "owner/repo" is not one, and neither is a mention. Inside a view |gf|
    does the same; see |forge-gf|.

    Anything naming nothing forge knows is a search, narrowing the list
    rather than opening one thing: >
        :Issue label:bug is:open
        :PR review-requested:@me
        :Issue label:"good first issue" no:assignee
<
    See |forge-search|.

    {target} is any of: >
        :PR @
        :Issue .
        :Issue 41138
        :Issue #41138
        :PR !123
        :Issue neovim/neovim#41138
        :PR group/subgroup/project!123
        :Issue neovim/neovim
        :Issue https://github.com/neovim/neovim/issues/41138
        :Issue forge://github.com/neovim/neovim/issues/41138
<
    A form naming no repository is answered by the one the CLI resolves; see
    |forge-repository|.

    ":Issue" will not open a pull or merge request and ":PR" will not open an
    issue. A bare number is taken as the collection of the command it was
    given to.

    |:command-modifiers| are honoured: >
        :vertical Issue 41310
        :tab PR 41138
        :botright Issue neovim/neovim
<
    The window is made once the forge answers, in the window the command was
    given in, so a request that fails leaves no window behind.

4. REPOSITORY                                               *forge-repository*

The repository is whichever gh or glab resolves in the current directory, so
forge agrees with every other command of theirs run there. In a fork that is
the base repository, where the items live.

The forge is chosen by host: gitlab.com is GitLab, and so is any host glab
holds a login for; everything else is GitHub. A target naming no repository
takes the host of the "upstream" remote, else "origin".

Requests are made from the directory of the current buffer, so a file opened
from another repository is asked about there. Buffers are filed under the
forge's spelling of the name, whatever was typed.

A bare |:PR| also needs the current branch. git answers first; in a colocated
jj repository the bookmark on the current change answers instead, and a change
wearing none is reported rather than guessed at. Reading a branch never writes
to the repository.

5. URIS                                                           *forge-uris*

Buffers are named with a "forge://" URI. Every view has exactly one name, and
that name is enough to rebuild it. >

    forge://{host}/{project}/{collection}            the whole list
    forge://{host}/{project}/{collection}?q={query}  the ones a search matches
    forge://{host}/{project}/{collection}/{number}   a single one
<
{host} is the forge, by hostname. {collection} is "issues" or "prs", and "prs"
holds merge requests on GitLab. {project} is "{owner}/{repo}", or a GitLab
path of any depth: >

    forge://github.com/neovim/neovim/prs/41370
    forge://gitlab.com/gitlab-org/cli/issues/8022
    forge://gitlab.com/group/subgroup/project/prs/123
<
A query is percent-encoded in the name, so |:edit| on one by hand wants the
"%" escaped: `:edit forge://github.com/a/b/issues?q=is:open\%20label:bug`.
Nothing that opens a view for you needs that.

|:edit| on one of these opens it from anywhere, and reloads it from inside. A
list holds every state there is; the page is not part of the name, so a reload
returns to the first. "R" keeps the page.

6. BUFFERS                                                     *forge-buffers*

A single item has a 'filetype' of "markdown", so existing markdown rendering
applies, and its comments are headings. A list has a 'filetype' of "forge".

Both are scratch buffers: 'buftype' is "nofile", 'readonly' is set,
'undolevels' is -1 and 'modeline' is off.

Window options are applied wherever a view appears and released when that
window shows something else. An item is set up to read as prose, a list to
hold one item to a line, each number drawn in the state of the item it names.

A buffer being fetched again sets 'busy' until the reply lands.

                                                                     *b:forge*
Every view buffer carries a `b:forge` dictionary. The 'winbar' is drawn from
it, and a user mapping may read it. Present in both shapes: >

    kind       "list" or "item"
    label      what the winbar calls it, e.g. "PR", "MR"
    repo       the project's full path
    url        the address the forge gave it
<
In a list, and only in one: >

    pages      the current page, e.g. "1/3", or "1/?" where the last
               page is not known
    total      how many the list holds in all, absent where that is
               not known
    query      the search narrowing it, empty when there is none
<
In an item, and only in one. The last three are a pull or merge request's: >

    tag        its number, e.g. "#41138", "!123"
    title      its title
    about      what the winbar says after the state, empty when the
               branches say it instead
    state      the state as shown, e.g. "OPEN", "MERGED", "NOT PLANNED"
    state_hl   the highlight group that state is drawn in
    badges     its extra winbar segments
    stat       what it measures, drawn against the right edge
    id         what a mutation names it by
    can_update whether the forge will let you change it
    oid        the head it was drawn from
    can_squash        whether the forge would take each of the three
    can_merge_commit  merges, weighed before the menu is drawn
    can_rebase
    can_bypass whether a merge would bypass something to happen
    merge      the commit message the forge would write, keyed by the
               method that would carry it, absent where it writes none
    can_auto   whether a merge may be set to wait, and whether one
    can_unauto already waiting may be called off
    auto       the method a waiting merge would use, absent when none
               is waiting
    queued     whether the base branch merges through a queue, and
    in_queue   whether this one is in it
    base       the branch it merges into
    head       the branch it merges from, prefixed with the owner when
               that is a fork
    remote     the repository "dd" and "dl" fetch it from
<
An item is its title, then who opened it and when, then what is known about
it, then its body and the conversation under it: >

    # Support file:// without netrw

    ▎ superatomic  MEMBER  4 days ago
      Assignees:  clason
      Type:       Enhancement
      Parent:     #32280
      Labels:     uri, lifecycle
      Milestone:  0.13

    Nvim supports opening files with file:// syntax.

    ## Comments (2)

    ▎ yochem  CONTRIBUTOR  3 days ago

    As file:// are just urls this should be added to net.lua.
<
A row appears only when there is something in it, and the column is as wide as
the widest row drawn. A pull or merge request says "Reviewers" instead of
"Type" and "Parent". On GitHub those are the ones still being waited on, a
request being dropped when its reviewer answers; on GitLab they are everyone
asked. A parent is written as the reference |gf| follows, not as the title it
stands for.

"Comments" is the conversation. A comment written against a line of the diff
is a review comment, and forge draws none of those: a change reviewed in the
diff shows fewer comments here than its own page does.

A bar starts anything somebody wrote, item and comment alike, because a body
is markdown and a heading in one would otherwise read as the start of another
comment. A login is drawn in the emphasis a colourscheme gives markdown, a
label or a milestone as a tag, and everything else on those lines is dimmed.
Underline is added to whatever can be followed, so what a thing is and what it
does are said separately.

What the forge would have linked in a body is marked there too: "@someone",
"#123", "!123", "owner/repo#4" and "group/project!123". Nothing inside a
fenced block is, since a forge links nothing there either and "@param" is not
a person. A reference is followed with |gf|; a mention leaves the editor, and
|gx| takes it to a profile on the host the body was written on, reading the
address off the mark rather than the text.

Every view sets a 'winbar': >

    ISSUES barrettruth/forge-fixture 1/2 (124)
    ISSUE #27 OPEN | a title that fits
    ISSUE #41309 NOT PLANNED | one nobody is going to do
    PR #151 MERGED | master <- a-branch                         +10 -2
    PR #152 OPEN | master <- them:their-branch CONFLICT FAILING | +7 -0
    MRS group/subgroup/project 1/1 (8)
    MR !12 OPEN | main <- a-branch                                +3 -1
<
A closed issue is drawn as the reason it closed, since each of those implies
closed, the way "MERGED" and "DRAFT" do for a pull or merge request.

An issue says its title there, and a pull or merge request says the branches
it joins, in git's order: what is merged into, then what merges. A title is in
the buffer anyway, and a branch is what tells one from another.

Only that part is ever truncated, so what an item is and how it stands survive
a narrow window. A diffstat is only a measure, so it goes to the right edge,
with a bar before it only when there is a badge to divide it from. A badge
appears only when it has something to say, so one that merges cleanly and
whose checks passed carries neither of those two. Its checks are "FAILING",
"PENDING" or "EXPECTED"; "dc" shows which.

Highlighting uses builtin |group-name| groups only.

7. MAPPINGS                                                   *forge-mappings*

    <CR>     <Plug>(forge-open)        Open the item under the cursor.
    o        <Plug>(forge-open-split)  The same, beside the list.
    gf       (see |forge-gf|)          Follow the reference under the cursor.
    -        <Plug>(forge-up)          Leave an item for its list.
    R        <Plug>(forge-refresh)     Fetch this view again, in place.
    ]i  [i   <Plug>(forge-next-page)   Page through a list. ]p and [p
             <Plug>(forge-prev-page)   in a pull or merge request list.
    ga       <Plug>(forge-create)      Start something new, on the forge.
    gX       <Plug>(forge-web)         Open this view in a browser.
    gy       <Plug>(forge-yank)        Yank this view's URL.
    cc       <Plug>(forge-act)         Do something to this item.
    dc       <Plug>(forge-checks)      Its checks, in ci.nvim.
    dd       <Plug>(forge-diff)        Its diff, in diffs.nvim.
    dl       <Plug>(forge-log)         Its commits, in fugitive.
    g?       <Plug>(forge-help)        This section.

                                                          *<Plug>(forge-help)*
                                                          *<Plug>(forge-open)*
                                                    *<Plug>(forge-open-split)*
                                                            *<Plug>(forge-up)*
                                                       *<Plug>(forge-refresh)*
                                                     *<Plug>(forge-next-page)*
                                                     *<Plug>(forge-prev-page)*
                                                        *<Plug>(forge-create)*
                                                           *<Plug>(forge-web)*
                                                          *<Plug>(forge-yank)*
                                                           *<Plug>(forge-act)*
                                                        *<Plug>(forge-checks)*
                                                          *<Plug>(forge-diff)*
                                                           *<Plug>(forge-log)*
Mappings are buffer-local and attached by URI, so none of them reach an
ordinary markdown file. A default is set only where nothing in that buffer
already maps the key and nothing already maps to the <Plug>; otherwise the
existing mapping stands. To rebind, map the |<Plug>| target: >lua
    vim.keymap.set('n', '<C-]>', '<Plug>(forge-open)')
<

"-" in a list does nothing: a list is the top.

"R" keeps the current page and cursor position; |:edit| and a new page both
start at the first line.

"ga" opens the forge's own page for a new one. The repository is the one the
view names rather than the current one, so a fork can propose a branch to what
it forked.

"gX" opens what the buffer shows, not what the cursor is on, and "gy" yanks
the URL it would have opened. "gy" takes the register it is given, so `"+gy`
reaches the system clipboard.

"cc" offers what the item can be asked to do as it stands, and does the one
picked. Everything in that menu writes, which is what the prompt says: >

    Change issue #27:
    Change pull request #151:
    Change merge request !12:
< What you may do is the forge's answer, not forge's guess at its rules. The
menu is |vim.ui.select()|, so it is whichever picker you already use. >

    any of them                 edit title and body
    an open issue               close as completed, close as not planned
    a closed issue              reopen
    an open pull/merge request  convert to draft, close, merge
    a draft                     mark ready for review, close
    a closed one                reopen
    a merged one                nothing
<
A merge is offered once per method the repository allows, narrowed on GitHub
by the base branch's ruleset: "Squash and merge", "Create a merge commit",
"Rebase and merge". One with conflicts offers none of them.

On GitHub, a base branch that merges through a queue refuses every direct
merge, so none of the three is offered there either. "Add to merge queue" is
offered instead, and "Remove from merge queue" once it is in one. Neither
takes a method or a message: how the queue merges is the queue's own setting.

A squash and a merge commit open the commit message to be written before they
are sent; see |forge-merge|. A rebase writes no commit and goes straight out.

github offers a merge that waits, and forge offers it once per method, above
the merges that happen now: >

    Enable auto-merge (squash)
< It is taken when github says the pull request may merge, and until then
"Disable auto-merge" calls it off. github only offers this on a pull request
it will not merge yet, so it appears where a merge is blocked — which is where
the bypass appears too, the two being the answers to the same thing: go past
the rule now, or wait for it. A waiting merge never bypasses; github does not
honour one when the time comes.

A merge that would go past a rule rather than satisfy it is named for it: >

    Squash and merge (bypass)
< That is a name and not another action: there is no separate admin merge, and
both names send the same thing. The suffix appears when github says the merge
would go past a rule you may bypass, and the plain name when it would not, so
the two are never offered together.

The merge names the head the view was drawn from, so a branch that moved since
then is refused rather than merged unseen. Everything else the forge decides
when asked: a merge it blocks is refused with its own reason.

On GitHub an issue closes with a reason, since a plain close means "completed"
whether or not that is true. Closing as a duplicate is left to github's own
page, which asks which issue.

                                                                  *forge-edit*
"Edit title and body" replaces the view, as "dd" and "dc" do, because nearly
all of what an item shows is the two. |CTRL-O| goes back to it. The buffer is
laid out as a commit message is: the first line is the title, and the body
follows a blank line.

Its 'winbar' is the item's own with the state swapped for the mode: >

    ISSUE #166 EDIT
    PR #151 EDIT
<

Writing sends it: ":w" and nothing else. Nothing is sent for an empty title.

The buffer lasts as long as it is on screen and no longer, so it never holds
anything staler than the item it was opened from. Until the forge says yes it
stays 'modified', and a refused write keeps what you wrote.

'modified' refuses ":q", ":bd" and ":enew". It does not refuse ":hide", which
takes the buffer off the screen and so throws the text away as surely as ":q!"
does. Keeping it instead would mean a buffer that is never abandoned, which
costs the refusal on the other three, so this is the one quiet way to lose
what you typed.

It is not a view: its name cannot rebuild it, and "R" and |:edit| do nothing
to it. The item is drawn again where it sits once the write lands, so it is
current by the time you go back to it.

                                                                 *forge-merge*
"Squash and merge" and "Create a merge commit" open the commit message they
would carry, in a split beside the item. It is laid out as a commit message
is: the subject on the first line, the body after a blank line.

On GitHub it starts as the message github itself would write, so a repository
that squashes to the pull request's description gets that, and one that
squashes to the branch's commit messages gets those. On GitLab it opens empty.

Its 'winbar' says which method, and says when the merge bypasses: >

    PR #151 SQUASH
    PR #151 MERGE COMMIT
    PR #174 SQUASH BYPASS
<
Writing sends it, as in |forge-edit|, and the buffer behaves as that one does.
Nothing is sent for an empty subject. The item is drawn again in its place
once the merge lands.

"cc" is bound in an item; "dc", "dd" and "dl" only in a pull or merge request.
"dc" and "dd" replace the view; ci.nvim returns with "-", and the way back
from a diff is |CTRL-O|.

"dl" splits instead. The log is >
    git log --stat --reverse base..head
<
"dd" and "dl" fetch both ends of it first, and share the one fetch. The refs
land under refs/forge/; no branch, tag or working tree is touched. This is the
only thing forge writes to a repository.

"dl" also sets `b:git_dir`, so `:Git` in the buffer aims at the repository the
refs were fetched into — the current one, not necessarily the one the view
names.

                                                                    *forge-gf*
|gf| follows the reference under the cursor, |CTRL-W_f| into a split, and in
Visual mode the selection. Nothing is bound; this is 'includeexpr'. A
reference naming no repository means the one whose view holds it, and
surrounding punctuation is left behind, so "(#123)", "`#123`" and "#123." all
follow to the same place.

|gf| takes the references ":Issue ." and ":PR ." take: "#123", "!123",
"owner/repo#4", "group/subgroup/project!123", a forge:// URI, and a github.com
URL. It differs in what it does with what is not one: a path is handed back to
Vim, so |gf| on an ordinary path in a body still opens the file.

"!123" is a merge request wherever it is read, and "#123" an issue — except on
GitHub, where issues and pull requests share one numbering and "#123" means
whichever collection the view holds.

In a list <CR> opens the item the line describes; |gf| opens the reference the
cursor is on, which inside a title may be another issue.

8. SEARCH                                                       *forge-search*

A {target} that names nothing else is passed to github as a search, in
github's own syntax and byte for byte, quoting and negation included. See
https://docs.github.com/en/search-github/searching-issues-and-pull-requests

On GitLab it is matched against the title and the description instead, and
none of what follows applies: there are no qualifiers there, so one typed is
looked for as text.

Two qualifiers are forge's rather than yours, and are dropped from whatever
you type: "repo:", "org:" and "user:", because a second repository would widen
a list past the one its name claims; and "is:issue", "is:pr", "type:issue" and
"type:pr", because |:Issue| showing pull requests would make the command a
lie. Repeating either of those in github's syntax widens rather than narrows,
which is why they cannot simply be added to.

"sort:updated-desc" is added when you give no "sort:" of your own, so a
narrowed list is ordered like a whole one.

A search reaches a thousand results however many it matches, so the page count
is what can be reached and the total is what was found: >

    ISSUES neovim/neovim is:issue 1/10 (14478)
<
An unknown qualifier is not an error to github; it is searched for as text,
and the answer is usually nothing found.

                                                     *forge-search-completion*
|c_CTRL-D| and <Tab> complete a qualifier, and its value where github's set of
them is closed — "is:", "no:", "in:", "state:", "reason:", "review:",
"status:", "linked:", "draft:", "archived:" and "sort:". A qualifier naming a
person completes to "@me" and nothing else. A negation completes the same.

Nothing else completes, and nothing asks github. A repository's labels,
milestones and people cannot be known without a request, and a request behind
<Tab> is either slow or answering from a copy that has gone stale.

==============================================================================
9. GITLAB                                                       *forge-gitlab*

A GitLab view says "merge request" where a GitHub one says "pull request",
writes "!" in front of a number instead of "#", and calls itself "MR" and
"MRS" in the 'winbar'. |:PR| is still the command that opens one, and "prs"
still the collection its name holds: >

    :PR !123
    :PR group/subgroup/project!123
    :edit forge://gitlab.com/group/subgroup/project/prs/123
<
A project's path carries as many segments as its groups nest, in a name, a
target and a reference alike.

What GitLab does not do:

  - a closed issue is "CLOSED" and nothing else. GitLab records no reason
    for a close, so there is one close and no "close as not planned".
  - a merge is a squash or a merge commit. There is no rebase, no merge that
    waits, and no merge train.
  - the commit message a merge would carry opens empty; GitLab does not say
    what it would have written.

==============================================================================
10. HEALTH                                                      *forge-health*

`:checkhealth forge` checks everything in |forge-requirements|. A missing
glab, like a missing optional plugin, is a warning rather than an error, and
names what it would have backed.
