1. INTRODUCTION                                                  *forge-intro*

Forge reads GitHub issues and pull requests into Neovim buffers. There are two
commands, |:Issue| and |:PR|; every other action is a mapping in the buffer
they open.

Requests go through the "gh" CLI. There is no setup() function and nothing to
configure.

==============================================================================
2. REQUIREMENTS                                           *forge-requirements*

  - Neovim 0.12 or newer
  - the "gh" CLI, authenticated (https://cli.github.com)

Three plugins are optional. Each backs one mapping; every other key works
without them, and |forge-health| reports which are missing.

  - ci.nvim, for "dc"
    https://forge.barrettruth.com/barrettruth/ci.nvim
  - diffs.nvim, for "dd"
    https://forge.barrettruth.com/barrettruth/diffs.nvim
  - vim-fugitive, for "dl"
    https://github.com/tpope/vim-fugitive

3. COMMANDS                                                   *forge-commands*

:Issue [{target}]                                                     *:Issue*
:PR [{target}]                                                           *:PR*
    Opens {target}. Without an argument, opens the list for the current
    repository.

    ":PR @" opens the pull request for the current change, spelled as git and
    jj both spell it. Only a pull request has one: nothing identifies the
    current issue, and ":Issue @" says so. A change with no pull request is
    not an error — "@" opens the page a new one arrives on, and gh pushes the
    branch on the way there.

    ":Issue ." and ":PR ." open the reference under the cursor, from any
    buffer: a source file, a commit message, a |:terminal| running
    "gh search". A reference is "#41138", "neovim/neovim#41138", a github.com
    URL or a forge:// URI. A bare "owner/repo" is not one, and neither is a
    mention. Inside a view, |gf| does the same without the command; see
    |forge-gf|.

    {target} is any of: >
        :PR @
        :Issue .
        :Issue 41138
        :Issue #41138
        :Issue neovim/neovim#41138
        :Issue neovim/neovim
        :Issue https://github.com/neovim/neovim/issues/41138
        :Issue forge://neovim/neovim/issues/41138
<
    A form that names no repository is answered by the one gh resolves. See
    |forge-repository|.

    A target naming the other kind is refused: ":Issue" will not open a pull
    request, and ":PR" will not open an issue. A bare number cannot be checked
    that way, because github numbers issues and pull requests from one counter
    and only github knows which a number belongs to.

    |:command-modifiers| are honoured: >
        :vertical Issue 41310
        :tab PR 41138
        :botright Issue neovim/neovim
<
    The window is made once github answers, in the window the command was
    given in. A request that fails leaves no window behind, and one overtaken
    by a later command does not take the window from it.

    A |:range| is accepted and ignored, so ":" from Visual mode is not an
    error.

4. REPOSITORY                                               *forge-repository*

Forge does not resolve the current repository itself. It sends gh's own
`{owner}` and `{repo}` placeholders and lets gh answer, so forge agrees with
every other gh command run in the same directory.

In a fork that means the base repository, the one a fork's issues and pull
requests actually live on. gh honours a default set with `gh repo set-default`
and otherwise prefers a remote named "upstream", then "github", then "origin".

Requests are made from the directory of the current buffer, so a file opened
from another repository is asked about there rather than wherever Nvim
started. The repository comes back with the answer, so a buffer is filed under
github's spelling of the name whatever was typed.

A bare |:PR| also needs the current branch. git answers first. In a colocated
jj repository git's HEAD is detached one commit behind the bookmark that names
the pull request, so jj answers instead: the branch is the bookmark on the
change being worked on, and a change wearing none is reported rather than
guessed at. Reading a branch never writes to the repository.

5. URIS                                                           *forge-uris*

Buffers are named with a "forge://" URI. Every view has exactly one name, and
that name is enough to rebuild it. >

    forge://{owner}/{repo}/issues           the open issue list
    forge://{owner}/{repo}/issues/closed    the closed issue list
    forge://{owner}/{repo}/issues/{number}  a single issue
    forge://{owner}/{repo}/prs              the open pull request list
    forge://{owner}/{repo}/prs/closed       the closed and merged list
    forge://{owner}/{repo}/prs/{number}     a single pull request
<
|:edit| on one of these opens it from anywhere, and reloads it from inside.
Which half of a collection a list holds is part of its name, so a reload
restores the same half. The page is not part of the name, so a reload returns
to the first; "R" keeps the page instead.

The path is close to github.com's but does not copy it. github spells a single
pull request "pull" and the list "pulls", and a closed list as a query rather
than a path; forge writes "prs" for both halves of the collection, and
"/closed" as a path. github's spelling appears only in the address "gX" opens.

6. BUFFERS                                                     *forge-buffers*

A single issue or pull request has a 'filetype' of "markdown", the shape
github returns it in, so any existing markdown rendering applies. Comments are
headings, so "]]" and "[[" move between them. A list has a 'filetype' of
"forge".

Both are scratch buffers: 'buftype' is "nofile", 'readonly' is set, and
'undolevels' is -1, so a refresh builds no unreachable undo history.
'modeline' is off, because a body is text written by a stranger.

Window options are applied wherever a view appears, in the buffer-local scope,
so a window releases them when it shows something else. An item is set up to
read as prose, a list to hold one item to a line.

A buffer being fetched again sets 'busy' until the reply lands.

                                                                     *b:forge*
Every view buffer carries a `b:forge` dictionary. The 'winbar' is drawn from
it, and a user mapping may read it. Present in both shapes: >

    kind       "list" or "item"
    label      what the winbar calls it, e.g. "PR"
    repo       "owner/repo"
    state      the state as shown, e.g. "OPEN", "MERGED", "open"
    state_hl   the highlight group that state is drawn in
<
In a list, and only in one: >

    pages      the current page, e.g. "1/3"
    total      how many the list holds in all
<
In an item, and only in one. The last two are a pull request's: >

    tag        its number, e.g. "#41138"
    title      its title
    badges     its extra winbar segments
    from       which half of a list it was opened from
    base       the branch it merges into
    head       the branch it merges from
<
Every view sets a 'winbar' naming it and giving the position within it: >

    ISSUES barrettruth/forge-fixture open 1/2 (124)
    ISSUE #27 OPEN | a title that fits
    PR #151 MERGED +10 -2 | another one
<
A finished load echoes nothing, because the winbar already reports it.
Messages are for problems.

Highlighting uses builtin |group-name| groups only, so no colorscheme needs to
know about forge.

7. MAPPINGS                                                   *forge-mappings*

    <CR>     <Plug>(forge-open)        Open the item under the cursor.
    o        <Plug>(forge-open-split)  The same, beside the list.
    gf       (see |forge-gf|)          Follow the reference under the cursor.
    -        <Plug>(forge-up)          Leave an item for its list.
    R        <Plug>(forge-refresh)     Fetch this view again, in place.
    g.       <Plug>(forge-state)       Toggle open and closed.
    ]i  [i   <Plug>(forge-next-page)   Page through a list. A pull
             <Plug>(forge-prev-page)   request list uses ]p and [p.
    ga       <Plug>(forge-create)      Start something new, on github.com.
    gx       <Plug>(forge-web-cursor)  Open the reference under the cursor
                                       on github.com.
    gX       <Plug>(forge-web)         Open this view on github.com.
    dc       <Plug>(forge-checks)      Its checks, in ci.nvim.
    dd       <Plug>(forge-diff)        Its diff, in diffs.nvim.
    dl       <Plug>(forge-log)         Its commits, in fugitive.
    g?       <Plug>(forge-help)        This section.

                                                          *<Plug>(forge-help)*
                                                          *<Plug>(forge-open)*
                                                    *<Plug>(forge-open-split)*
                                                            *<Plug>(forge-up)*
                                                       *<Plug>(forge-refresh)*
                                                         *<Plug>(forge-state)*
                                                     *<Plug>(forge-next-page)*
                                                     *<Plug>(forge-prev-page)*
                                                        *<Plug>(forge-create)*
                                                           *<Plug>(forge-web)*
                                                    *<Plug>(forge-web-cursor)*
                                                        *<Plug>(forge-checks)*
                                                          *<Plug>(forge-diff)*
                                                           *<Plug>(forge-log)*
Mappings are buffer-local and attached by URI, so none of them reach an
ordinary markdown file. A default is set only where nothing in that buffer
already maps the key and nothing already maps to the <Plug>; otherwise the
existing mapping stands. To rebind, map the |<Plug>| target: >lua
    vim.keymap.set('n', '<C-]>', '<Plug>(forge-open)')
<

"-" goes to the half of the list the item was opened from. An item opened by
name came from nowhere and goes to the open list. A list is the top, so "-" in
one does nothing.

"R" keeps the current page and cursor position. A view opens at the top unless
it is being returned to; a new page, the other half of a list, and a reload
with |:edit| all start at the first line.

"ga" opens github's own page for a new issue or pull request, which applies
whichever template the repository defines and accepts attachments. The
repository is the one the view names rather than the current one, so a fork
can propose a branch to what it forked.

"gx" and "gX" divide the cursor from the buffer, as |gf| and "gX" do. "gx"
opens the reference under the cursor, or the one selected in Visual mode:
"#41138", "neovim/neovim#41138", or an "@mention", which goes to a profile.
Anything else is handed back to |gx| unchanged, so an ordinary URL still opens
and a |gx| of your own still wins. The label of a markdown link is handed back
too, because its target may name another repository and Neovim reads that.

"gX" opens what the buffer shows, not what the cursor is on. The page is not
carried, because a page is not part of a view's name.

"dc", "dd" and "dl" are bound only in a pull request: an issue has no CI, no
diff and no commits of its own. "dc" and "dd" replace the view, being the same
pull request seen differently. ci.nvim's own "-" is pointed back at the pull
request; diffs.nvim has no notion of where it was opened from, so the way back
from a diff is |CTRL-O|.

"dl" splits instead, leaving the pull request beside it. The log is >
    git log --stat --reverse base..head
<
")" and "(" step between commits and |<CR>| opens the one under the cursor;
"o", "O" and "gO" open it in a split, a tab and a vertical split. |CTRL-O|
returns to the log at the commit it was left on. Fugitive's "-" opens the
parent commit instead, walking out of the range. "g?" lists the rest of
fugitive's keys.

"dd" and "dl" fetch both ends of the pull request first, and share the one
fetch. The refs land under refs/forge/, which nothing else writes; no branch,
tag or working tree is touched. This is the only thing forge writes to a
repository.

"dl" also sets `b:git_dir` on the pull request buffer, so `:Git` there aims at
the repository the refs were fetched into — the current one, which is not
necessarily the one the view names.

                                                                    *forge-gf*
|gf| follows the reference under the cursor, |CTRL-W_f| follows it into a
split, and in Visual mode |gf| follows the selection. Nothing is bound; this
is 'includeexpr'. A reference naming no repository means the one whose view
holds it. Punctuation wrapped around a reference is left behind, so "(#123)",
"`#123`" and "#123." all follow to the same place.

|gf| does not take a github.com URL. |gx| opens one in the browser, ":Issue ."
and ":PR ." open one here.

<CR> and |gf| are not the same key twice. In a list <CR> opens the item the
line describes, wherever on the line the cursor sits; gf opens the reference
the cursor is on, which inside a title may be another issue entirely.

8. HEALTH                                                       *forge-health*

`:checkhealth forge` checks everything in |forge-requirements|. A missing
optional plugin is a warning rather than an error, and names the mapping it
would have backed.
