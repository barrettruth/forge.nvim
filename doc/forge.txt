1. INTRODUCTION                                                  *forge-intro*

Read GitHub issues and pull requests in Neovim. Two commands, |:Issue| and
|:PR|; everything else is a mapping inside the buffer they open.

Forge delegates to the "gh" CLI and renders what it returns. There is nothing
to configure and no setup() to call.

==============================================================================
2. REQUIREMENTS                                           *forge-requirements*

  - Neovim 0.12 or newer
  - the "gh" CLI, authenticated (https://cli.github.com)

Two plugins are optional. Each backs one mapping; every other key works
without them, and |forge-health| reports which is missing.

  - ci.nvim, for "dc"
    https://forge.barrettruth.com/barrettruth/ci.nvim
  - diffs.nvim, for "dd"
    https://forge.barrettruth.com/barrettruth/diffs.nvim

3. COMMANDS                                                   *forge-commands*

:Issue [{target}]                                                     *:Issue*
:PR [{target}]                                                           *:PR*
    Open {target}. Without an argument, either command opens its list for the
    repository you are in.

    :PR @ opens the pull request for the change you are on, spelled as git
    and jj both spell it. Only a pull request has one: nothing identifies the
    issue you are on, and :Issue @ says so. A change with no pull request yet
    is not an error — "@" opens the page one arrives on, and gh pushes the
    branch on the way there.

    :Issue . and :PR . open the reference under the cursor, from any buffer:
    a source file, a commit message, a |:terminal| running `gh search`. A
    reference is "#41138", "neovim/neovim#41138", a github.com URL or a
    forge:// URI. A bare "owner/repo" is not one, and neither is a mention.
    Inside a view, |gf| does the same without the command; see |forge-gf|.

    {target} is any of: >
        :PR @
        :Issue .
        :Issue 41138
        :Issue #41138
        :Issue neovim/neovim#41138
        :Issue neovim/neovim
        :Issue https://github.com/neovim/neovim/issues/41138
        :Issue forge://neovim/neovim/issues/41138
<
    A form that names no repository is answered by the one gh resolves. See
    |forge-repository|.

    A target that names the other kind is refused: :Issue will not open a
    pull request, and :PR will not open an issue. A bare number cannot be
    checked that way, because github numbers issues and pull requests from
    one counter and only github knows which a number is.

    |:command-modifiers| are honoured, so the view opens where you say: >
        :vertical Issue 41310
        :tab PR 41138
        :botright Issue neovim/neovim
<
    The window is made once github has answered, and in the window the
    command was given in. A request that fails leaves no window behind, and
    one overtaken by a later command does not take the window from it.

    A |:range| is accepted and ignored, so ":" from Visual mode is not an
    error.

4. REPOSITORY                                               *forge-repository*

Forge does not work out which repository you are in. It sends gh's own
`{owner}` and `{repo}` placeholders and lets gh answer, so forge agrees with
every other gh command you run in the same directory.

In a fork that means the base repository, the one a fork's issues and pull
requests actually live on. gh honours a default set with `gh repo set-default`
and otherwise prefers a remote named "upstream", then "github", then "origin".

Requests are made from the directory of the buffer you are in, so a file
opened from another repository is asked about there rather than wherever nvim
was started. The repository comes back with the answer, so a buffer is filed
under github's spelling of the name, whatever you typed.

A bare |:PR| also needs to know which branch you are on. git is asked first.
In a colocated jj repository git's HEAD is detached one commit behind the
bookmark that names the pull request, so jj is asked instead: the branch is
the bookmark on the change you are working on, and a change wearing none is
reported rather than guessed at. Reading a branch never writes to the
repository.

5. URIS                                                           *forge-uris*

Buffers are named with a "forge://" URI. Every view has exactly one name, and
that name is enough to rebuild it. >

    forge://{owner}/{repo}/issues           the open issue list
    forge://{owner}/{repo}/issues/closed    the closed issue list
    forge://{owner}/{repo}/issues/{number}  a single issue
    forge://{owner}/{repo}/prs              the open pull request list
    forge://{owner}/{repo}/prs/closed       the closed and merged list
    forge://{owner}/{repo}/prs/{number}     a single pull request
<
|:edit| on one of these opens it from anywhere, and reloads it from inside.
Which half of a collection a list holds is part of its name, so a reload
brings back what you were looking at. Which page you were on is not, so a
reload starts again at the first; "R" keeps it.

github spells a single pull request "pull" and the list "pulls". Forge writes
"prs" for both, and the singular appears only in the address "gX" opens.

6. BUFFERS                                                     *forge-buffers*

A single issue or pull request has a 'filetype' of "markdown", which is the
shape github returns it in, so whatever already renders markdown for you
renders it here. Comments are headings, so "]]" and "[[" walk between them. A
list has a 'filetype' of "forge".

Both are scratch buffers: 'buftype' is "nofile", 'readonly' is set, and
'undolevels' is -1, so refreshing does not build an undo history you cannot
reach anyway. 'modeline' is off, because a body is text a stranger wrote.

A window is set up when a view appears in it, in the buffer-local scope, so
the settings are given back when that window shows something else. An item
gets 'wrap', 'linebreak' and 'breakindent'; a list gets 'nowrap' and
'cursorline', because there one line is one item.

While a view is being fetched again, its buffer's 'busy' flag is set.

                                                                     *b:forge*
Every view buffer carries a `b:forge` dictionary. The 'winbar' is drawn from
it, and a mapping of your own may read it: >

    kind       "list" or "item"
    label      what the winbar calls it, e.g. "PR"
    repo       "owner/repo"
    state      the state as shown, e.g. "OPEN", "MERGED", "open"
    state_hl   the highlight group that state is drawn in
    tag        an item's number, e.g. "#41138"
    title      an item's title
    badges     an item's extra winbar segments
    pages      which page of a list, e.g. "1/3"
    total      how many the list holds in all
    from       which half of a list an item was opened from
    base       the branch a pull request merges into
    head       the branch a pull request merges from
<
Every view sets a 'winbar' saying what it is and where in it you are: >

    ISSUES barrettruth/forge-fixture open 1/2 (124)
    ISSUE #27 OPEN | a title that fits
    PR #151 MERGED +10 -2 | another one
<
Because the winbar holds it, nothing is reported when a view loads. Messages
are for problems.

Highlighting uses builtin |group-name| groups only, so a colorscheme needs to
know nothing about forge. A number is "Tag", a repository "Directory", a state
"OkMsg", "ErrorMsg" or "Special", and anything secondary "Comment".

7. MAPPINGS                                                   *forge-mappings*

    <CR>     <Plug>(forge-open)        Open the item under the cursor.
    o        <Plug>(forge-open-split)  The same, beside the list.
    gf       (see |forge-gf|)          Follow the reference under the cursor.
    -        <Plug>(forge-up)          Leave an item for its list.
    R        <Plug>(forge-refresh)     Fetch this view again, in place.
    g.       <Plug>(forge-state)       Toggle open and closed.
    ]i  [i   <Plug>(forge-next-page)   Page through a list. A pull
             <Plug>(forge-prev-page)   request list uses ]p and [p.
    ga       <Plug>(forge-create)      Start something new, on github.com.
    gX       <Plug>(forge-web)         Open this view on github.com.
    dc       <Plug>(forge-checks)      Its checks, in ci.nvim.
    dd       <Plug>(forge-diff)        Its diff, in diffs.nvim.
    g?       <Plug>(forge-help)        This section.

                                                          *<Plug>(forge-help)*
                                                          *<Plug>(forge-open)*
                                                    *<Plug>(forge-open-split)*
                                                            *<Plug>(forge-up)*
                                                       *<Plug>(forge-refresh)*
                                                         *<Plug>(forge-state)*
                                                     *<Plug>(forge-next-page)*
                                                     *<Plug>(forge-prev-page)*
                                                        *<Plug>(forge-create)*
                                                           *<Plug>(forge-web)*
                                                        *<Plug>(forge-checks)*
                                                          *<Plug>(forge-diff)*
Mappings are buffer-local and attached by URI, so nothing here reaches an
ordinary markdown file. A default is only set when nothing in that buffer
already maps the key and nothing already maps to the <Plug>; otherwise your
mapping stands. To rebind, map the |<Plug>| target: >lua
    vim.keymap.set('n', '<C-]>', '<Plug>(forge-open)')
<

"-" goes to the half of the list you came from. An item opened by name came
from nowhere, and goes to the open list. A list is the top, so "-" in one does
nothing.

"R" keeps the page you are on and where you were reading it. A view starts at
the top unless you are returning to something you were already reading; a new
page, the other half of a list, or a reload with |:edit| all start at the
first line.

"ga" opens github's own page for a new issue or pull request, which is the
form: it applies whichever template the repository defines and takes
attachments. The repository is the one the view names rather than the one you
are standing in, so a fork can propose a branch to what it forked.

"gX" opens what the buffer shows, not what the cursor is on. Which page you
are on is not carried, because a page is not part of a view's name.

"dc" and "dd" are bound only in a pull request: an issue has no CI and no
diff. Both replace the view rather than splitting beside it, being the same
pull request seen differently. ci.nvim's own "-" is pointed back at the pull
request; diffs.nvim has no notion of where it was opened from, so the way back
from a diff is |CTRL-O|.

"dd" fetches both ends of the pull request first, because diffs.nvim draws
from your object store rather than from a patch. The refs land under
refs/forge/, which nothing else writes; no branch, tag or working tree is
touched. This is the only thing forge writes to a repository.

                                                                    *forge-gf*
|gf| follows the reference under the cursor, |CTRL-W_f| follows it into a
split, and in Visual mode |gf| follows the selection. Nothing is bound; this
is 'includeexpr'. A reference naming no repository means the one whose view
you are in. The punctuation prose wraps a reference in is left behind, so
"(#123)", "`#123`" and "#123." all follow to the same place.

|gf| does not take a github.com URL. |gx| opens one in the browser, ":Issue ."
and ":PR ." open one here.

<CR> and |gf| are not the same key twice. In a list <CR> opens the item the
line describes, wherever on the line the cursor sits; gf opens the reference
the cursor is on, which inside a title may be another issue entirely.

==============================================================================
8. HEALTH                                                       *forge-health*

`:checkhealth forge` reports the Neovim version, whether "gh" is present and
authenticated, and whether ci.nvim and diffs.nvim are available. The last two
are warnings rather than errors: both are optional, and forge says which key
stops working without each.
