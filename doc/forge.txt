1. INTRODUCTION                                                  *forge-intro*

Work with GitHub issues in Neovim. Forge delegates to the "gh" CLI and renders
what it returns; there is nothing to configure and no setup() to call.

==============================================================================
2. REQUIREMENTS                                           *forge-requirements*

  - Neovim 0.11 or newer
  - the "gh" CLI, authenticated (https://cli.github.com)

==============================================================================
3. COMMANDS                                                   *forge-commands*

:PR [{target}]                                                           *:PR*
:Issue [{target}]                                                     *:Issue*
    Open {target}. Without an argument, :Issue opens the issue list, and :PR
    opens the pull request for the branch you are on. Only a pull request has
    an obvious referent: nothing identifies "the current issue".

    In a jj repository a bookmark belongs to a change rather than trailing
    behind you, so the branch is the bookmark on the change you are working
    on. A change wearing none is reported, not guessed at: the nearest
    bookmark below belongs to a different change, and proposing it would open
    a pull request for someone else's branch.

    {target} is any of: >
        :Issue 41138
        :Issue #41138
        :Issue neovim/neovim#41138
        :Issue neovim/neovim
        :Issue https://github.com/neovim/neovim/issues/41138
        :Issue forge://neovim/neovim/issues/41138
<
    A form that names no repository is answered by the one gh resolves. See
    |forge-repository|.

    |:command-modifiers| are honoured, so the view opens where you say: >
        :vertical Issue 41310
        :tab PR 41138
        :botright Issue neovim/neovim
<
    The window is made once github has answered, and in the window the command
    was given in. A request that fails leaves no window behind, and one that
    succeeds while you are reading something else does not steal the window
    you moved to.

    A target that names the other kind is refused: :Issue will not open a pull
    request, and :PR will not open an issue. A bare number cannot be checked
    that way, because github numbers issues and pull requests from one counter
    and only github knows which a number is.

4. REPOSITORY                                               *forge-repository*

Forge does not work out which repository you are in. It sends gh's own
`{owner}` and `{repo}` placeholders and lets gh answer, which means forge
agrees with every other gh command you run in the same directory, for free.

That matters most in a fork. gh answers with the base repository, the one a
fork's issues and pull requests actually live on. It honours a default set
with `gh repo set-default`, and otherwise prefers a remote named "upstream",
then "github", then "origin". Reading a remote here instead would answer a
fork with the wrong repository, which is a silently empty list rather than an
error.

The repository comes back with the view, so it is github's spelling of the
name that a buffer is filed under, whatever you typed. Requests are made from
the directory of the buffer you are in, so a file opened from another
repository is asked about there rather than wherever nvim was started.

A bare |:PR| additionally needs to know which branch you are on. git is asked
first. In a colocated jj repository git's HEAD is detached one commit behind
the bookmark that names the pull request, so git there is not merely silent
but wrong, and jj is asked for the nearest bookmark instead. Reading a branch
never writes to the repository.

5. URIS                                                           *forge-uris*

Buffers are named with a "forge://" URI, which is the plugin's addressing
scheme. Every view has exactly one name, and that name is enough to rebuild
it. >

    forge://{owner}/{repo}/issues           the open issue list
    forge://{owner}/{repo}/issues/closed    the closed issue list
    forge://{owner}/{repo}/issues/{number}  a single issue
    forge://{owner}/{repo}/prs            the open pull request list
    forge://{owner}/{repo}/prs/closed     the closed and merged list
    forge://{owner}/{repo}/prs/{number}   a single pull request
    forge://{owner}/{repo}/issues/new     an issue not filed yet
<
The path after the scheme is github.com's own, so a forge:// URI is a page you
already know how to read. GitHub numbers a single issue under the plural
"issues" too. It numbers a single pull request under the singular "pull",
which forge does not copy: a collection is plural here whatever it holds, and
the singular appears only in the address "gX" opens.

Which issues a list holds is part of its name, so reloading one with |:edit|
brings back what you were looking at. Which page you were on is not, so a
reload starts again at the first.

6. MAPPINGS                                                   *forge-mappings*

A single issue has a filetype of "markdown", because that is the shape GitHub
returns it in. A list has a filetype of "forge".

Every view sets a 'winbar' saying what it is and where in it you are: >

    ISSUES barrettruth/forge-fixture open 1/2 (124)
    ISSUE #27 OPEN
    PRS barrettruth/forge-fixture open 1/1 (14)
    PR #151 MERGED +10 -2
<
Because the winbar holds it, nothing is reported when a view loads. Messages
are for problems, not for progress that succeeded.

Highlighting uses builtin |group-name| groups only, so a colorscheme needs to
know nothing about forge. An issue number is "Tag" wherever it appears, a
repository "Directory", a state "OkMsg" or "ErrorMsg", and anything secondary
"Comment". Lists are marked with extmarks recorded as each line is built,
rather than matched by pattern afterwards, so a title that happens to contain
"#12" or end in "(3)" is never mistaken for one.

Mappings are buffer-local and defined through <Plug> so they can be replaced.
A default is only set when nothing in that buffer already maps the key, and
nothing already maps to the <Plug>; otherwise your mapping stands. They are
attached by URI rather than by filetype, so nothing here reaches an ordinary
markdown file.

                                                          *<Plug>(forge-help)*
g?                      This list, for the buffer you are in.

                                                          *<Plug>(forge-open)*
<CR>                    In an issue list, open the issue under the cursor.

                                                    *<Plug>(forge-open-split)*
o                       In an issue list, open the issue under the cursor in
                        a split, keeping the list visible.

                                                            *<Plug>(forge-up)*
-                       Leave an item for the list it belongs to, closed or
                        open, whichever you came from. An item opened by name
                        came from nowhere, and goes to the open list. A list
                        is the top, so "-" in a list does nothing.

                                                       *<Plug>(forge-refresh)*
R                       Fetch this view again, keeping the page you are on.
                        |:edit| also refetches, but rebuilds from the name and
                        so returns to the first page.

                                                     *<Plug>(forge-next-page)*
                                                     *<Plug>(forge-prev-page)*
]i  [i                  A hundred issues at a time, forwards and backwards. ]p
[p                  The same, through pull requests.

                                                         *<Plug>(forge-state)*
g.                      Swap between open and closed, from the first page.
                        Closed pull requests include merged ones, which is the
                        split github's own Closed tab makes.

                                                        *<Plug>(forge-create)*
ga                      Start something new in the collection you are looking
                        at. Templates come from your checkout, so a repository
                        you are only browsing offers none and the draft starts
                        empty. Reading an issue                         *form*
                        parser for yaml; without one, forms are skipped and
                        forge says so rather than offering you nothing.
                        |:checkhealth| reports whether you have it.

                        One template is used without asking, several
                        are chosen between by name. A template that names
                        itself is called that; one that does not, which is
                        every pull request template, is called after its file.

                        A draft is an ordinary buffer holding the markdown
                        that will be filed. Guidance a form carries is shown
                        beside it rather than written into it, so there is
                        nothing to delete before filing, and a "*" marks an
                        answer github will insist on.

                        A pull request also needs two branches. The one you
                        are on is proposed, and github says what it merges
                        into; the winbar names both. Being on that branch
                        already, with nothing to propose, is refused rather
                        than sent.

                        Writing the buffer files it: "ZZ" creates and closes,
                        ":w" creates and leaves you on what you made, and "ZQ"
                        discards. An answer left blank becomes "_No response_",
                        which is what github writes for one.

                                                           *<Plug>(forge-web)*
gX                      Open this view on github.com: what the buffer shows,
                        not what the cursor is on. Which page you are on is
                        not carried, because a page is not part of a view's
                        name. A draft opens the form it started from, rather
                        than the chooser.

7. HEALTH                                                       *forge-health*

`:checkhealth forge` reports the Neovim version, whether "gh" is present, and
whether it is authenticated.
