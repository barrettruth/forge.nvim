1. INTRODUCTION                                                  *forge-intro*

Forge reads GitHub issues and pull requests into Neovim buffers. There are two
commands, |:Issue| and |:PR|; every other action is a mapping in the buffer
they open. There is no setup() function and nothing to configure.

==============================================================================
2. REQUIREMENTS                                           *forge-requirements*

  - Neovim 0.12 or newer
  - the "gh" CLI, authenticated (https://cli.github.com)

Optional, one mapping each:

  - ci.nvim, for "dc"
    https://forge.barrettruth.com/barrettruth/ci.nvim
  - diffs.nvim, for "dd"
    https://forge.barrettruth.com/barrettruth/diffs.nvim
  - vim-fugitive, for "dl"
    https://github.com/tpope/vim-fugitive

3. COMMANDS                                                   *forge-commands*

:Issue [{target}]                                                     *:Issue*
:PR [{target}]                                                           *:PR*
    Opens {target}. Without an argument, opens the list for the current
    repository.

    ":PR @" opens the pull request for the current change. Nothing identifies
    the current issue, and ":Issue @" says so. A change with no pull request
    yet opens the page a new one arrives on, and gh pushes the branch.

    ":Issue ." and ":PR ." open the reference under the cursor, from any
    buffer. A reference is "#41138", "neovim/neovim#41138", a github.com URL
    or a forge:// URI; a bare "owner/repo" is not one, and neither is a
    mention. Inside a view |gf| does the same; see |forge-gf|.

    {target} is any of: >
        :PR @
        :Issue .
        :Issue 41138
        :Issue #41138
        :Issue neovim/neovim#41138
        :Issue neovim/neovim
        :Issue https://github.com/neovim/neovim/issues/41138
        :Issue forge://neovim/neovim/issues/41138
<
    A form naming no repository is answered by the one gh resolves; see
    |forge-repository|.

    ":Issue" will not open a pull request and ":PR" will not open an issue. A
    bare number is not checked, because only github knows which it is.

    |:command-modifiers| are honoured: >
        :vertical Issue 41310
        :tab PR 41138
        :botright Issue neovim/neovim
<
    The window is made once github answers, in the window the command was
    given in, so a request that fails leaves no window behind.

4. REPOSITORY                                               *forge-repository*

The repository is whichever gh resolves in the current directory, so forge
agrees with every other gh command run there. In a fork that is the base
repository, where the issues and pull requests live.

Requests are made from the directory of the current buffer, so a file opened
from another repository is asked about there. Buffers are filed under github's
spelling of the name, whatever was typed.

A bare |:PR| also needs the current branch. git answers first; in a colocated
jj repository the bookmark on the current change answers instead, and a change
wearing none is reported rather than guessed at. Reading a branch never writes
to the repository.

==============================================================================
5. URIS                                                           *forge-uris*

Buffers are named with a "forge://" URI. Every view has exactly one name, and
that name is enough to rebuild it. >

    forge://{owner}/{repo}/issues           every issue
    forge://{owner}/{repo}/issues/{number}  a single issue
    forge://{owner}/{repo}/prs              every pull request
    forge://{owner}/{repo}/prs/{number}     a single pull request
<
|:edit| on one of these opens it from anywhere, and reloads it from inside. A
list holds every state there is; the page is not part of the name, so a reload
returns to the first. "R" keeps the page.

6. BUFFERS                                                     *forge-buffers*

A single issue or pull request has a 'filetype' of "markdown", so existing
markdown rendering applies, and its comments are headings. A list has a
'filetype' of "forge".

Both are scratch buffers: 'buftype' is "nofile", 'readonly' is set,
'undolevels' is -1 and 'modeline' is off.

Window options are applied wherever a view appears and released when that
window shows something else. An item is set up to read as prose, a list to
hold one item to a line, each number drawn in the state of the item it names.

A buffer being fetched again sets 'busy' until the reply lands.

                                                                     *b:forge*
Every view buffer carries a `b:forge` dictionary. The 'winbar' is drawn from
it, and a user mapping may read it. Present in both shapes: >

    kind       "list" or "item"
    label      what the winbar calls it, e.g. "PR"
    repo       "owner/repo"
<
In a list, and only in one: >

    pages      the current page, e.g. "1/3"
    total      how many the list holds in all
<
In an item, and only in one. The last two are a pull request's: >

    tag        its number, e.g. "#41138"
    title      its title
    state      the state as shown, e.g. "OPEN", "MERGED", "NOT PLANNED"
    state_hl   the highlight group that state is drawn in
    badges     its extra winbar segments
    base       the branch it merges into
    head       the branch it merges from
<
Every view sets a 'winbar': >

    ISSUES barrettruth/forge-fixture 1/2 (124)
    ISSUE #27 OPEN
    PR #151 MERGED +10 -2
    PR #152 OPEN CONFLICT FAILING +7 -0
<
An item's title is the first line of its buffer, so the winbar does not repeat
it. A badge appears only when it has something to say, so a pull request that
merges cleanly and whose checks passed carries neither of those two. Its
checks are "FAILING", "PENDING" or "EXPECTED"; "dc" shows which.

Highlighting uses builtin |group-name| groups only.

7. MAPPINGS                                                   *forge-mappings*

    <CR>     <Plug>(forge-open)        Open the item under the cursor.
    o        <Plug>(forge-open-split)  The same, beside the list.
    gf       (see |forge-gf|)          Follow the reference under the cursor.
    -        <Plug>(forge-up)          Leave an item for its list.
    R        <Plug>(forge-refresh)     Fetch this view again, in place.
    ]i  [i   <Plug>(forge-next-page)   Page through a list. A pull
             <Plug>(forge-prev-page)   request list uses ]p and [p.
    ga       <Plug>(forge-create)      Start something new, on github.com.
    gX       <Plug>(forge-web)         Open this view on github.com.
    dc       <Plug>(forge-checks)      Its checks, in ci.nvim.
    dd       <Plug>(forge-diff)        Its diff, in diffs.nvim.
    dl       <Plug>(forge-log)         Its commits, in fugitive.
    g?       <Plug>(forge-help)        This section.

                                                          *<Plug>(forge-help)*
                                                          *<Plug>(forge-open)*
                                                    *<Plug>(forge-open-split)*
                                                            *<Plug>(forge-up)*
                                                       *<Plug>(forge-refresh)*
                                                     *<Plug>(forge-next-page)*
                                                     *<Plug>(forge-prev-page)*
                                                        *<Plug>(forge-create)*
                                                           *<Plug>(forge-web)*
                                                        *<Plug>(forge-checks)*
                                                          *<Plug>(forge-diff)*
                                                           *<Plug>(forge-log)*
Mappings are buffer-local and attached by URI, so none of them reach an
ordinary markdown file. A default is set only where nothing in that buffer
already maps the key and nothing already maps to the <Plug>; otherwise the
existing mapping stands. To rebind, map the |<Plug>| target: >lua
    vim.keymap.set('n', '<C-]>', '<Plug>(forge-open)')
<

"-" in a list does nothing: a list is the top.

"R" keeps the current page and cursor position; |:edit| and a new page both
start at the first line.

"ga" opens github's own page for a new issue or pull request. The repository
is the one the view names rather than the current one, so a fork can propose a
branch to what it forked.

"gX" opens what the buffer shows, not what the cursor is on.

"dc", "dd" and "dl" are bound only in a pull request. "dc" and "dd" replace
the view; ci.nvim returns with "-", and the way back from a diff is |CTRL-O|.

"dl" splits instead. The log is >
    git log --stat --reverse base..head
<
"dd" and "dl" fetch both ends of the pull request first, and share the one
fetch. The refs land under refs/forge/; no branch, tag or working tree is
touched. This is the only thing forge writes to a repository.

"dl" also sets `b:git_dir`, so `:Git` in the buffer aims at the repository the
refs were fetched into — the current one, not necessarily the one the view
names.

                                                                    *forge-gf*
|gf| follows the reference under the cursor, |CTRL-W_f| into a split, and in
Visual mode the selection. Nothing is bound; this is 'includeexpr'. A
reference naming no repository means the one whose view holds it, and
surrounding punctuation is left behind, so "(#123)", "`#123`" and "#123." all
follow to the same place.

|gf| does not take a github.com URL; ":Issue ." and ":PR ." do.

In a list <CR> opens the item the line describes; |gf| opens the reference the
cursor is on, which inside a title may be another issue.

==============================================================================
8. HEALTH                                                       *forge-health*

`:checkhealth forge` checks everything in |forge-requirements|. A missing
optional plugin is a warning rather than an error, and names the mapping it
would have backed.
